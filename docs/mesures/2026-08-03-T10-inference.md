**La distribution est la sortie ; l'équité est une commodité.** L'interface est construite pour
rendre le piège de T10 inatteignable : `gn_evaluate` **ne peut pas** rendre une équité, seulement
cinq probabilités. Le moteur de référence fait l'inverse — `nn_forward` rend une équité money et
ne remplit les cinq probabilités que si on le lui demande. Le match play a besoin de la
distribution ; un scalaire a déjà jeté ce que la table d'équité de match consomme.

## L'ordre des cinq sorties, et comment il est établi

```
probs[0]  P(gain)                  probs[3]  P(perte-gammon ou pire)
probs[1]  P(gain-gammon ou mieux)  probs[4]  P(perte-backgammon)
probs[2]  P(gain-backgammon)
```

**Imbriquées, pas exclusives** : `probs[1]` compte les backgammons, `probs[0]` compte tout.

Cet ordre n'est pas pris sur parole dans un commentaire. Il est **forcé par la formule d'équité**
de `vendor/backgammon-ai-engine/c_inference/nn_eval.c:217` :

```
E = 2·p0 + p1 + p2 − p3 − p4 − 1
```

qui est la conséquence algébrique de cette lecture, et d'aucune autre :

```
  1·(p0−p1) + 2·(p1−p2) + 3·p2            gagner simple, gammon, backgammon
− 1·((1−p0)−p3) − 2·(p3−p4) − 3·p4        perdre des trois mêmes façons
= 2·p0 + p1 + p2 − p3 − p4 − 1                                            ✓
```

Permutez les cinq, l'identité tombe. `model.py:284` le dit aussi en toutes lettres — *« canonical
order: P(win), P(wg), P(wbg), P(lg), P(lbg) »* — mais c'est l'algèbre qui rend la chose
**vérifiable**.

## Résultats

### Parité PyTorch — ✅

| | |
|---|---|
| Corpus | **2 000 positions**, graine `20260803`, les deux couleurs au trait |
| Comparaisons | 2 000 × 5 = **10 000 sorties** |
| **`max|Δ|` mesuré** | **`4,768e-07`** |
| Critère | `< 1e-5` |

Les deux côtés reçoivent **le même vecteur de 196 flottants**, produit par notre encodeur C.

> **Ce que ce test ne prouve pas, et il faut le dire.** Il isole le **chargement des poids et la
> passe avant**. Il ne dit **rien** de la justesse de l'encodage : si les deux côtés partageaient
> un encodeur faux, il passerait quand même. La justesse de l'encodage est le travail de T02, et
> `test_codec.py` la vérifie contre `encoding.py` à `max|Δ| = 0` — c'est là qu'elle est établie,
> pas ici.

L'écart n'est pas nul par construction : les poids sont en float32 des deux côtés, mais l'ordre
des opérations diffère — BLAS chez PyTorch, boucles C chez nous.

### Les inégalités d'événements imbriqués — ✅, et le test n'est pas décoratif

Les cinq sorties viennent de **cinq sigmoïdes indépendantes** : rien dans le réseau ne garantit
que `P(gain-gammon) ≤ P(gain)`. C'est le clamp de `nn_eval.c:211-215` qui l'impose.

Un test qui vérifie une propriété que rien ne menace ne prouve rien. Nous avons donc mesuré la
sortie **avant** clamp :

> **16 positions sur 500 violaient les inégalités** avant écrêtage.

Le clamp travaille sur ~3 % du corpus. Sans lui, ces positions rendraient une non-distribution.

### Une probabilité négative, trouvée par le test — corrigée

Le test d'imbrication a d'abord échoué sur une position réelle du corpus :

```
Position(W au trait, off=(0,13), …)
  P(gain)          = 1,5432609e-10
  P(perte-gammon)  = 1,0
```

**Le moteur n'a pas fait d'erreur.** En float32 — son arithmétique — `1.0f − 1,54e-10f` vaut
exactement `1.0f` : l'inégalité `p3 ≤ 1−p0` tient, et le clamp n'avait rien à corriger. C'est la
vérification, menée en float64, qui examinait un calcul n'ayant jamais eu lieu.

Mais l'affaire ne s'arrête pas là, et c'est le point utile : **un consommateur qui dénesterait en
double obtiendrait `P(perte simple) = (1−p0) − p3 = −1,5e-10`.** Une probabilité négative sur le
chemin de la table d'équité de match — minuscule, silencieuse, et exactement le mode de
défaillance que `CLAUDE.md` refuse.

Deux corrections, une par face du problème :

- **`gn_probs_are_nested` et `Evaluation.is_nested` comparent en float32**, celle du moteur.
- **`gn_probs_exclusive` a été ajouté** : il dénest en double et **plancher à zéro**, rendant les
  six issues mutuellement exclusives dont T32 et T34 auront besoin. La soustraction fragile est
  écrite **une fois**, à un endroit, plutôt que dans chaque consommateur.

Vérifié sur le corpus entier : aucune issue négative, et somme = 1 à `1e-6` près. Un contrôle
croisé compare en outre les deux chemins vers l'équité — depuis les imbriquées et depuis les
exclusives — qui doivent coïncider.

### Refuser plutôt qu'approximer — ✅

`gn_network_load` **refuse** : un modèle qui n'est pas prob5 (il sortirait une équité agrégée,
inutilisable en match et silencieusement), un modèle dont la taille d'entrée n'est pas 196 (il a
été entraîné sur un autre encodage), un fichier tronqué, un magic erroné. Chacun a son test, et le
cas prob5 est éprouvé en exportant réellement `cubeful_money_512_512_256.pt` et en constatant le
refus.

## Deux corrections en marge

**GCC 16 voit ce que GCC 8.5 ne peut pas voir.** `src/gn_position_id.c:25` déclarait son alphabet
base64 en `char[64]`, l'initialiseur remplissant exactement le tableau et perdant le NUL final —
`-Wunterminated-string-initialization`, ajouté dans GCC 15. Inoffensif à l'usage (seuls 64 octets
sont lus), mais `CLAUDE.md` tient nos sources au **silence complet du compilateur**, et cet
avertissement est invisible sur `mochy`. Corrigé en `char[65]`.

**`test_codec.py` sautait dix-sept tests pour en protéger un.** L'oracle `gnubg_nn` était importé
au niveau du module alors qu'un seul test s'y confronte. Sur la machine de bureau — sans oracle,
par conception — **la vérification la plus critique du projet passait au vert sans rien
vérifier**. L'import est descendu dans une fixture. `make test` passe ici de **4 tests exécutés à
34**.

## Configuration de mesure

AMD Ryzen 7 PRO 6850U (16 fils), 14,4 Gio, **pas de GPU**, Linux 7.1.5-arch1-2, Python 3.13.14,
PyTorch **2.13.0+cpu**, NumPy 2.5.1, GCC 16.1.1, Emscripten 6.0.5-git, `gnubg-nn` absent
(délibérément — `ORACLE=0`). Reproductible par `make env`.

Le `Makefile` a été rendu conscient de la machine : `PYTHON_SYS`, `TORCH_CPU` et `ORACLE`. Sans
cela, `pip install torch` aurait tiré la build CUDA — environ 5 Gio de paquets `nvidia-*` — sur
une machine sans GPU et dont le disque est à 97 %. La commande d'amorçage de la piste B est :

```bash
make setup PYTHON_SYS=python3.13 TORCH_CPU=1 ORACLE=0
```

## Ce qui reste ouvert

- **Le chargement depuis la mémoire.** `nn_load` lit un chemin de fichier. En WebAssembly le
  modèle arrivera par `fetch` ; le contournement prévu est d'écrire les octets dans le MEMFS
  d'Emscripten, où `fopen` fonctionne. **À vérifier en T20, pas supposé.**
- **`compile_commands.json`** absent : `clangd` ne trouve pas les en-têtes vendorés et signale des
  erreurs que le `Makefile` ne produit pas. Confort d'édition, sans effet sur le build.

Suite : **T20**, le build WebAssembly.
